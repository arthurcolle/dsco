# Executing a selected Chimera plan

Lingo can select a bounded direct plan and explicitly execute that same plan:

```lua
local c=require("lingo.chimera")
local plan=c.preferences{
  allowed_models={"openai/gpt-4.1-mini"},require_known_price=true,
}:plan{
  task="A small, source-grounded analysis task",
  strategy="direct",max_calls=1,max_output_tokens=384,
  max_expected_cost_usd=.01,max_worst_case_cost_usd=.01,
}
local receipt=plan:execute()
return receipt.completion.execution
```

The plan remains a JSON-compatible observation with its existing `policy`,
`request` and `decision` fields. `execute()` privately retains the original
inputs and selected contract. Editing displayed fields cannot retarget it;
execution accepts no override arguments. Select a new plan to change the task.

## Contract and compatibility

`chimera_route` retains its planning-only behavior. Eligible Router decisions
now additionally contain `execution_contract`: format `dsco.chimera.direct/1`,
a unique `execution_id`, `request_sha256` and `plan_sha256`. Older servers and
plans outside the execution profile can still be inspected, but cannot execute
through this method.

The separate governed tool `chimera_execute` accepts `action="execute"`, the
original `policy` and `request`, and that exact contract as `expected_plan`.
It uses only the configured `CHIMERA_HOST` origin and host-owned authentication;
scripts cannot supply endpoints, credentials, stream settings, tools or provider
overrides. The execution profile requires one user text message, a direct plan,
one call, at most 512 output tokens, a known price, and both planner cost limits
at or below $0.01. Task text is limited to 16 KiB, native input to 32 KiB and
the complete response to 128 KiB. Native connection timeout is three seconds;
overall timeout is 55 seconds around the Router's existing 45-second stage bound.

Router recomputes the decision once and compares the captured hashes **before**
credential provisioning, credit admission or provider dispatch. The plan hash
includes the executable plan, inference artifacts and actual planning catalog
identity. A mismatch returns `plan_changed`; it does not silently execute a
different selection. The existing direct executor performs one OpenRouter
request without Router retries, model fallback or OpenRouter hosting fallback.

Authenticated tenant identity is required. The existing `fabric_runs` table
atomically consumes an execution ID within its organization/project scope. A
duplicate returns `execution_already_submitted`, even after an uncertain first
attempt. A rejected calculation/scenario call does not consume the Lua handle;
a returned native receipt does. No automatic retry or new execution ID is
generated by `execute()`.

## What the receipt establishes

Success has `profile="chimera_completion"`, `executed=true` and the full native
completion under `completion`. Its `execution` record contains the exact
contract, dispatch count, disabled-fallback policy and `measured` evidence:

- Requested model and provider-reported model are separate fields.
- Provider response ID, Router request ID, fabric run and attempt IDs identify
  the actual attempt.
- Elapsed milliseconds measure the bounded provider stage.
- `usage` preserves upstream usage before Router settlement can change costs.
  Missing usage is `null`, not zero inferred spend.

Planner budgets are estimates, **not hard guarantees about actual provider
billing**. The receipt states `budget_basis="planner_estimate_not_billing_guarantee"`.
Provider-reported `usage.cost` and its upstream cost details can differ; preserve
them separately. They are neither an invoice reconciliation nor a verified
measure of model quality. A timeout, oversized response or malformed completion
after dispatch yields `outcome_unknown`; retain the execution ID and inspect its
run rather than repeat the call. At-most-once Router dispatch does not establish
physical provider completion.

## Verification and actual outcome

`tests/test_lingo_chimera_execute.py` exercises 14 native-binary checks, including
private input capture, scenario rejection without consumption, exact request
repetition, wrong hashes/models/counts, malformed/oversized responses, scope
denial, unknown usage and explicit execution errors. Router's
`tests/test_guarded_chimera.py`, together with its existing plan-identity tests,
passes 22 checks covering real planning, drift, limits, durable replay rejection
and the single-attempt transport path. These tests use counted transport fixtures
and do not claim provider inference.

The explicit paid verifier is `scripts/verify_lingo_chimera_execution.py`.
It reads the current public catalog, constrains the named inexpensive model,
starts an isolated authenticated Router, uses an ephemeral encrypted BYOK row,
performs one call, checks duplicate-ID rejection and captures fabric evidence.
It never automatically retries. `--prior` retains a previous result and
`--model openai/gpt-4.1-mini` makes escalation an explicit new plan.

The [analysis example](../examples/lingo/chimera-analysis.lingo) stores immutable
observations, calculates acceptance and explanations as ordinary Lingo values,
and reopens a snapshot at the same ValueAddress. Passing its acceptance checks
establishes structure and coverage of the named source symbols; semantic
correctness still requires review.

Actual reports from September 10 are in
`reports/lingo-chimera-execution-20260910/`. The first `gpt-4.1-nano` completion
and the explicit `gpt-4.1-mini` escalation both completed through their selected
plans. Both produced useful source descriptions but failed the required output
shape. The shared world correctly retains both rejections. The mini run's
duplicate was refused with HTTP 409 and its database retained exactly one run
and one attempt. Combined provider-reported `usage.cost` was $0.001264626.
These are successful execution proofs and failed task-acceptance outcomes;
the raw model outputs are not relabeled as accepted artifacts.

An explicit subsequent **pure** adaptation recognizes mini's exact checks-map
shape and derives a separate artifact with a deterministic two-item array.
The original summary, risk and invariant strings are unchanged; the same
acceptance function accepts the derived artifact while both raw verdicts remain
rejected. `adaptation.json` retains the adapter/version, source execution ID,
ValueAddresses, dependency explanation and reloaded snapshot. This step used the
installed binary with NET disabled and zero tool calls. Its accepted output is
`accepted-analysis.json`; no further inference was performed.
