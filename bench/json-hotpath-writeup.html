Performance / dsco-cli

Three small changes that made our agent's JSON path 3–30× faster

CNEON / SSE2JSON
On the per-turn hot loop that every agent, and every swarm, pays for.

dsco-cli is a coding agent written in C. Run a single agent and it feels fast enough that nobody thinks about it. Fan out to a swarm and the story changes. Dozens of agents, each grinding through its own tool loop, and the per-turn cost stops being a rounding error. It becomes the bill.

So I went looking for the work that happens on every turn of every agent, no matter which model is answering. That work is pure CPU we spend on our own hardware. Two functions stood out, both in the JSON layer. Neither is glamorous. Between them they were doing a lot of avoidable work.

The short version. Reading fields out of a JSON object allocated a heap buffer for every key it walked past. That stops, and it's 2.8× faster. Escaping text into a JSON string ran one byte at a time, and decoding a string back out did too. Both go sixteen bytes at a time instead, worth 9.2× and 30×. Every one of the three produces the same bytes as the code it replaced.

Where the time actually goes

An agent turn has an obvious expensive part, which is waiting on the model. It also has a boring part nobody profiles. You build the request, you read the response, and both run locally on every turn. That work grows with the conversation. Two things dominate it.

  • Pulling fields out of the response and out of each tool call, through json_get_str, json_get_int, and friends.
  • Serializing the whole conversation back into the next request. That means escaping every message into a JSON string with jbuf_append_json_str.

Both were written the straightforward way years ago and never touched again. That's usually where the easy wins are hiding.

1. Stop allocating just to compare a key

The scalar field accessors re-scan the object from the top on every call. That's fine, even optimal, when you want a single field. The problem was how they matched keys. Here is the original find_key, lightly trimmed. 

static const char *find_key(const char *p, const char *key) {
    p = skip_ws(p);
    while (*p && *p != '}') {
        if (*p == '"') {
            char *k = NULL;
            const char *after = parse_string(p, &k);   // <-- mallocs a decoded copy
            /* ... */
            if (k && strcmp(k, key) == 0) {
                free(k);
                return after;
            }
            free(k);                                    // <-- ...just to throw it away
            after = skip_value(after);
            /* advance to next key */
        } else {
            p++;
        }
    }
    return NULL;
}

parse_string decodes a JSON string into a freshly allocated, escape-expanded buffer. find_key called it on every key it stepped over. Allocate a copy, run a strcmp, free the copy, move on. Pull eight fields out of a sixteen-key object and you have done well over a hundred malloc and free pairs to read eight values.

One fact makes this cheap to fix. JSON keys almost never contain escape sequences. A key is nearly always a plain identifier like "max_tokens". So compare the raw bytes in place, and fall back to the decoding path only when the key actually holds a backslash. The common case turns into a length check and a memcmp, with no allocation at all. 

/* Scan past a JSON string literal. On return [*cs, *ce) is the raw content and
 * *simple is true iff it had no backslash escape (so the raw span == the value). */
static const char *scan_string(const char *p, const char **cs, const char **ce, bool *simple) {
    p++;                          /* past opening quote */
    *cs = p;
    bool esc = false;
    while (*p && *p != '"') {
        if (*p == '\\') { esc = true; p++; if (!*p) break; }
        p++;
    }
    *ce = p;
    *simple = !esc;
    return (*p == '"') ? p + 1 : p;
}

/* ...inside find_key: */
const char *cs, *ce; bool simple;
const char *after = scan_string(p, &cs, &ce, &simple);
bool matched;
if (simple) {
    matched = ((size_t)(ce - cs) == keylen) && memcmp(cs, key, keylen) == 0;
} else {
    char *k = NULL;              /* rare: escaped key, decode exactly as before */
    parse_string(p, &k);
    matched = (k && strcmp(k, key) == 0);
    free(k);
}

That's the whole idea. The escaped-key path stays exactly as it was, so nothing about the output changes. The common path just stopped touching the allocator.

2. Escape a string 16 bytes at a time

The second function escapes arbitrary text into a JSON string literal. It runs on every message when we build a request, so its input adds up to the whole conversation. Here is how it looked. 

void jbuf_append_json_str(jbuf_t *b, const char *s) {
    jbuf_append_char(b, '"');
    const unsigned char *p = (const unsigned char *)s;
    while (*p) {
        if (*p == '"')       { jbuf_append(b, "\\\""); p++; }
        else if (*p == '\\') { jbuf_append(b, "\\\\"); p++; }
        else if (*p == '\n') { jbuf_append(b, "\\n");  p++; }
        /* ...other escapes, UTF-8 validation... */
        else { jbuf_append_char(b, (char)*p); p++; }   // <-- the common case
    }
    jbuf_append_char(b, '"');
}

For ordinary text, which is almost all of it, every byte took that last branch. jbuf_append_char does a bounds check and writes a NUL terminator on each call. A kilobyte of plain ASCII became a thousand branch-and-append round trips to emit a kilobyte.

The fix is the standard escaping move. Bulk-copy the run of bytes that need no escaping, and stop only when you hit one that does. How long is the next safe run? That's the kind of byte-classification a SIMD lane sweep answers well. A byte is unsafe when it's a control character below 0x20, a quote, a backslash, or has the high bit set, which means it needs UTF-8 validation. Everything else copies verbatim.

We already had a small portable SIMD header covering NEON and SSE2, with a scalar fallback, and almost nothing used it. Here is the new primitive. The NEON path is shown, and the SSE2 and scalar paths live next to it. 

/* Count leading bytes that can be copied verbatim into a JSON string:
 * printable ASCII (0x20..0x7E) except '"' and '\'. */
static inline size_t dsco_simd_json_safe_run(const char *base, size_t len) {
    const uint8_t *p = (const uint8_t *)base;
    size_t i = 0;
#if DSCO_SIMD_NEON
    const uint8x16_t lo = vdupq_n_u8(0x20), hi = vdupq_n_u8(0x7e);
    const uint8x16_t q = vdupq_n_u8('"'), bs = vdupq_n_u8('\\');
    for (; i + 16 <= len; i += 16) {
        uint8x16_t v = vld1q_u8(p + i);
        uint8x16_t bad = vcltq_u8(v, lo);      /* < 0x20  controls        */
        bad = vorrq_u8(bad, vcgtq_u8(v, hi));  /* > 0x7e  high bytes + DEL */
        bad = vorrq_u8(bad, vceqq_u8(v, q));   /* '"'                     */
        bad = vorrq_u8(bad, vceqq_u8(v, bs));  /* '\\'                    */
        if (vmaxvq_u8(bad) == 0) continue;     /* all 16 safe, keep going */
        /* first bad lane: narrow each 0xFF lane to a nibble, ctz/4 = index */
        uint8x8_t nb = vshrn_n_u16(vreinterpretq_u16_u8(bad), 4);
        uint64_t m = vget_lane_u64(vreinterpret_u64_u8(nb), 0);
        return i + ((size_t)__builtin_ctzll(m) >> 2);
    }
#endif
    for (; i < len; i++) {
        uint8_t c = p[i];
        if (c < 0x20 || c > 0x7e || c == '"' || c == '\\') return i;
    }
    return i;
}

On x86 the same classification is even tidier. A signed cmplt(v, 0x20) flags both the control bytes and the high bytes in one instruction, because 0x80..0xFF are negative as signed bytes. The escaping loop then becomes a run-scan plus one memcpy per run, and the original per-byte logic handles only the bytes that really need it.

3. Decode the same way you encode

The escaping win has an obvious twin. If writing a JSON string was slow one byte at a time, so was reading one. parse_string, the function behind json_get_str, runs for every string value pulled out of a response. It decoded character by character into a growing buffer, and clocked the same 0.51 GB/s.

The fix mirrors the encoder. Bulk-copy the run of ordinary characters up to the next quote, backslash, or terminating NUL, and drop into the scalar path only for real escape sequences. One wrinkle makes this harder than the encoder, though.

The encoder knew its input length up front, so its SIMD loop could stop a clean sixteen bytes before the end. The decoder can't. It gets a pointer into a NUL-terminated buffer with no length, and a sixteen-byte vector load starting near the end could stride into the next memory page and fault on a byte the program was never going to read. That's the hazard that makes a naive SIMD strlen crash.

The fix is the one libc uses. Only ever issue 16-byte-aligned loads, and ignore the lanes before where you actually started. A page is a multiple of sixteen, so an aligned sixteen-byte block never straddles two pages. The block holding your terminator always sits fully inside the page you were already reading. No length needed, and no page ever gets touched that your own bytes don't reach. 

static inline size_t dsco_simd_json_unescaped_run(const char *p) {
    const uint8_t *s = (const uint8_t *)p;
    const uint8x16_t q = vdupq_n_u8('"'), bs = vdupq_n_u8('\\'), z = vdupq_n_u8(0);
    uintptr_t addr = (uintptr_t)s;
    const uint8_t *base = (const uint8_t *)(addr & ~(uintptr_t)15);   /* align down */
    size_t off = (size_t)(addr - (uintptr_t)base);
    uint8x16_t v = vld1q_u8(base);                                    /* aligned load */
    uint8x16_t m = vorrq_u8(vorrq_u8(vceqq_u8(v,q), vceqq_u8(v,bs)), vceqq_u8(v,z));
    uint8x8_t nb = vshrn_n_u16(vreinterpretq_u16_u8(m), 4);
    uint64_t bits = vget_lane_u64(vreinterpret_u64_u8(nb), 0) & (~0ULL << (off*4));
    if (bits) return ((size_t)__builtin_ctzll(bits) >> 2) - off;      /* mask lanes before p */
    for (const uint8_t *cur = base + 16;; cur += 16) {                /* now fully aligned */
        v = vld1q_u8(cur);
        m = vorrq_u8(vorrq_u8(vceqq_u8(v,q), vceqq_u8(v,bs)), vceqq_u8(v,z));
        if (vmaxvq_u8(m) == 0) continue;
        nb = vshrn_n_u16(vreinterpretq_u16_u8(m), 4);
        bits = vget_lane_u64(vreinterpret_u64_u8(nb), 0);
        return (size_t)(cur - s) + ((size_t)__builtin_ctzll(bits) >> 2);
    }
}

Thirty times, and the biggest of the three. Decoding has no escaping work to do on the output side, so it's pure scan-and-copy, which is what the vector unit is for. To check the alignment trick was actually safe and not just lucky, the decoder ran against an unmapped guard page with its terminator placed at every offset in the last forty bytes before the boundary. Thirty-two placements, zero faults. The 200,000-case differential fuzz, run over escapes, \u sequences, lone surrogates, and valid surrogate pairs, matched the original byte for byte.

Under the hood: what the object code actually does

Wall-clock numbers are the outcome. They don't explain themselves. Both changes get a lot more convincing once you look at what the compiler emitted and what the process does at runtime.

find_key: counting the allocations that disappear

The point of the key-matching change wasn't instruction count, it was allocator traffic. And the allocations don't happen in find_key itself. They happen one level down, in parse_string. To measure them I redirected malloc and free in the JSON translation unit to counting wrappers, then ran 100,000 iterations of the same five-field read, two strings and three ints.

Versionmallocs / 100k readsPer read
Original4,400,00044
In-place compare200,000222× fewer

Forty-four allocations to read five fields. Each read walked the object from the top, and every key it stepped over got decoded into a fresh heap buffer and freed a moment later. The two that survive in the new version aren't waste. They're the two string values we asked for and hand back to the caller. The three integer reads now allocate nothing, where before each one allocated once per key it passed. Same answers, 22× less garbage through the allocator.

jbuf_append_json_str: reading the emitted NEON

The escaping change is the opposite kind of story. No allocation difference, all instruction mix. The classifier compiles to a tight vector loop. Here is the core of what clang -O3 -march=native emitted on arm64. 

    movi.16b  v3, #129              ; 0x81
    movi.16b  v4, #161              ; 0xA1
    movi.16b  v5, #34               ; '"'
    movi.16b  v6, #92               ; '\'
    ldr       q0, [x21, x23]        ; load 16 bytes
    add.16b   v1, v0, v3            ; byte + 0x81
    cmhi.16b  v1, v4, v1            ; 0xA1 >u (byte+0x81)   -> control OR high, in ONE compare
    cmeq.16b  v2, v0, v5            ; == '"'
    cmeq.16b  v0, v0, v6            ; == '\'
    orr.16b   v0, v2, v0
    orr.16b   v0, v0, v1            ; combined "unsafe" mask
    umaxv.16b b1, v0                ; any lane set?  (fast reject)
    shrn.8b   v0, v0, #4            ; narrow each 0xFF lane to a nibble

There is a nice piece of compiler work in there. I wrote the "is this byte a control character or a high byte" test as two separate unsigned comparisons, below 0x20 or above 0x7e. The compiler saw that as a single range test and folded it into add #0x81 followed by one cmhi #0xA1. Shift the byte so the safe printable range lands in a contiguous window, then do one unsigned compare. Two comparisons became one. I didn't ask for that. Recognizing the range idiom is what a good backend does once you've written the classification without branches.

Here is the shape that matters. The original loop did roughly one branch and one bounds-checked byte append per input byte. This loop classifies sixteen bytes with about eleven vector instructions, and when they're all safe, which is the common case, it takes a single umaxv fast-reject and moves on to bulk-copy the whole run. The per-byte overhead is gone. What's left is basically the memory bandwidth of the copy, which is why the throughput lands near 4.7 GB/s instead of 0.5.

Static instruction count actually went up. The function grew from about 294 to 364 instructions, because the SIMD fast path sits next to the untouched scalar path that still handles the escapes and the UTF-8. More static code, far less dynamic work. Bigger function, faster function.

Proving it didn't change the output

A faster escaper that emits different bytes isn't a faster escaper. It's a bug. The only result that matters for any of these changes is that the new code produces exactly what the old code did. So the old jbuf_append_json_str got pulled out under a different name and run side by side against the new one over 400,000 randomized inputs, biased toward the bytes that break things: control characters, quotes, backslashes, high bytes, truncated and invalid UTF-8, lone surrogates, and 0x7F. 

FUZZ: 400k random + edge cases BYTE-IDENTICAL

The key matcher got the same treatment. Prefix keys, where "ab" must not match "abc". Escaped keys, where "abc" decodes to "abc". Empty keys, nested objects and arrays as values, and unterminated input. All identical to the original.

The full suite is 5221 of 5222 passing. The one failure is a trace-logging test that fails the same way on a clean checkout with none of these changes applied. Pre-existing, and nothing to do with JSON. I would rather say that plainly than round it up.

Why bother, at this size

Nanoseconds per call sounds like the kind of thing you're not supposed to care about. The reason to care is the multiplier. This code runs on every field read and every message serialized, on every turn, for every agent. When you're trying to run a big swarm cheaply, the floor is set by exactly this kind of unglamorous per-turn work. The floor had a couple of feet of slack in it.

None of the three is clever. One deletes allocations that never needed to happen. The other two let the CPU look at sixteen bytes at once instead of one. Most wins at this layer look like that. Not a new algorithm, just noticing that the old code was politely doing far more work than the problem asked for.
